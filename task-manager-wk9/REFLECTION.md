# PA9 Reflection

## 1. What was the root cause of BUG-17, and which files were involved? Why would fixing only the stats count have been the wrong fix?

The root cause was in `app/services/tasks.py`: the `complete_task` function set `task.status = TaskStatus.DONE` (the string `"done"`) but `GET /stats` and `GET /tasks?status=completed` both look for the string `"completed"`. So a task marked complete was written with a status value that nothing else in the app considered completed. The files involved were `app/services/tasks.py` (the write), `app/services/stats.py` (the read), `app/models.py` (the status enum), and `app/routes/tasks.py` (the thin pass-through). fixing only the stats count would have made `GET /stats` show the right number, but `GET /tasks?status=completed` would still return [] and any client reading the task's status would see `done` instead of `"completed"` we'd be patching a symptom on one screen while the actual bad data was still being written.

## 2. Did a Drill test fail after your fix? If so, why was updating that test the right call here, when "do not modify the tests" was the rule in Drill?

No drill test failed after this fix. The Phase A regression test (`tests/test_bug17.py`) started as a failing test and became the proof the fix worked. The drill rule "do not modify the tests" is about not changing tests to hide a bug not about never touching tests at all. If a drill test had been asserting that `complete_task` write  was`"done"`, that test would have been pinning the buggy behavior, and updating it would have been correct. In this case, no such test existed so I didn't have to make that call.

## 3. What should happen to tasks already stored in a real database with the old status value?

Existing rows with `"done"` should be migrated to `"completed"` with a oneoff SQL update (`UPDATE task SET status = 'completed' WHERE status = 'done';`), run against the production database once before the fixed code ships. This makes every future query an exact-string match which avoids the trap of "forgetting to also accept 'done" that caused BUG-17 in the first place. The alternative making the stats and filter code accept both values works but requires every future query to remember the rule. The migration should be run inside a transaction with a backup, and the `TaskStatus.DONE` enum value should only be removed, after the migration is verified, otherwise old rows or the old mobile client would start failing validation.

## 4. In B3, what did the hook report, and what did Claude do with it? How is that different from you running the tests after Claude finishes?

The hook reported an `F401 'os' imported but unused` error with the exact file and line and exited with code 2. So claude saw the failure directly in the same turn. Claude responded by removing the `import os` line and re-running the edit.The hook fired again on the second edit, ran `ruff check .` and `pytest`, and this time exited 0 because both passed. The difference from me running tests manually is the feedback loop. If I run `pytest` after Claude finishes, I'm a human in the loop, and I have to notice a failure, decide what it means, and start a new Claude turn. With the hook the failure reaches Claude *inside the same tool call*, so Claude can fix it before I ever see the code, the cost of each iteration drops from one full turn to one edit.

## 5. Why did you write characterization tests (C2) before refactoring? What would the hook have told you during C3 without them?

Characterization tests pin down the current behavior of a function so that a refactor, which accidentally changes behavior shows up as a test failure. Before C2 `app/services/stats.py` was at 93% coverage lines 23 and 39 were untested so I could not have known whether the refactor preserved behavior for those cases. The characterization tests, 19 of them, including an empty database case and edge cases for overdue rules pushed coverage to 100% and made the refactor a mechanical change. If the refactor broke anything, `pytest` would fail, without those tests, the Phase B hook would still have run `pytest` after every edit, but `pytest` would have had nothing to check against the refactored code except the small handful of existing smoke tests, so the hook could easily have passed while a subtle behavior change (example - the overdue rule for `"done"` tasks) went unnoticed. The characterization tests are what gave the hook something meaningful to guard.
