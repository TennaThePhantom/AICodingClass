# Reflection MCP Servers

## 1 Schema design decision

When I designed the Zod schemas for the two tools the biggest choice was using `z.enum(['open', 'in_progress', 'completed'])` for the status field instead of just `z.string()`. There is a real trade off here. On one hand the enum stops typos and data that doesn't seems right. If someone asks Claude to "set task 3 to done" it can't accidentally write "done" into a column that expects "completed", because Zod rejects it before the SQL even runs. It also makes the tool explain itself, Claude can see the three valid values from the schema, and picks the right one without guessing. The cost is flexibility. If I later add a new status like "blocked" or "archived" I have to edit `index.js`, and restart the server, and any caller that doesn't know about the new value still gets rejected. For the title field, I would make the opposite choice, a free text string is fine there, because titles are written by users and are unpredictable and validation should only check length or weird characters.

## 2 MCP approach vs REST API

Calling an MCP server and calling a REST API from a prompt look kind of the same from the outside, both are just "Claude calls a tool and gets a result" but the inside is different. With MCP the tool schema is defined, inside the server using Zod and Claude Code finds it automatically when it connects. The prompt doesn't have to explain what arguments a tool takes because the schema is machine readable. With a REST API Claude has to build an HTTP request using whatever docs are in the prompt or system context, and it needs to know the URL, the headers, the body format and the error codes ahead of time. MCP's advantages are that discovery and validation are built in and the server can keep a database connection, or cache alive between calls and the transport is the same so the same server works in Claude Code Claude Desktop and\or any other MCP client. REST's advantages are universality any language any client can call it with curl, statelessness (easy to test easy to scale) and inspectability, every request is a normal HTTP call that can be logged and replayed. For a local SQLite tool like `task-db-server`, MCP is clearly the right pick, but for a public facing web service that lots of clients/Users hit REST would be better.

## 3 A missing capability

The one thing I wish `task-db-server` had is a `create_task(title, assigned_to, due_date)` tool ,so Claude could add new tasks not just read and update them. To add it as a third MCP tool I would follow the same pattern as the other two. I would add `server.tool('create_task', 'create a new task', { title z.string().min(1).describe('Task title'), assigned_to z.string().optional().describe('assignee'), due_date: z.string().regex(/^^\d{4}-\d{2}-\d{2}$/).optional().describe('due date YYYY-MM-DD') }, async ({ title, assigned_to, due_date}) => { ... })`. Inside the handler I would open the database, run `INSERT INTO tasks (title, assigned_to, due_date, status) VALUES (?, ?, ?, 'open')` grab the new id from `info.lastInsertRowid` close the database, and return `Task N created with status: open`. The regex on due_date is important because without it Claude could write a bad date pattern and the pattern check costs nothing. The same key and audit log stuff from `update_task_status` would apply too, and I would probably want a dry run mode, so Claude could preview what a create or update will do before actually committing it.
